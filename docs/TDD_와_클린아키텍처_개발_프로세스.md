# TDD와 클린 아키텍처 기반 개발 프로세스 논의

이 문서는 TDD와 클린 아키텍처를 적용하여 프로젝트를 개발하는 과정에 대한 논의를 요약한 것입니다.

## 1. TDD의 시작점: 어떤 일을 해야 하는가?

TDD(Test-Driven Development) 사이클(Red-Green-Refactor)에 따라, 가장 먼저 해야 할 일은 **핵심 비즈니스 로직에 대한 실패하는 테스트를 작성하는 것**입니다.

- **테스트 대상:** `Domain` 계층의 핵심 로직 (`PortfolioCalculator.cs`)
- **테스트 위치:** `tests` 프로젝트 (`PortfolioCalculatorTests.cs`)
- **첫 시나리오:** 가장 기본적이면서 핵심적인 기능. (예: "포트폴리오와 목표 비중이 주어졌을 때, 각 자산별 차이(Gap)를 정확하게 계산하는가?")

## 2. 엔티티(Entity) 정의 방식: 점진적 설계

**"처음부터 모든 것을 정의하는 것이 아니라, 테스트에 필요한 최소한의 필드만 추가하며 점진적으로 완성해나가는 방식"**이 TDD의 핵심입니다.

- **YAGNI (You Ain't Gonna Need It):** 실패하는 테스트가 증명하기 전까지는 코드를 작성하지 않는 원칙.
- **단순함과 집중:** 현재 해결해야 할 문제에만 집중하게 하여 복잡도를 낮춥니다.
- **점진적 설계 (Emergent Design):** 테스트 케이스라는 구체적인 요구사항에 따라 설계가 자연스럽게 완성됩니다.

## 3. 개발 순서: 왜 Domain 계층부터 시작하는가?

클린 아키텍처에서 개발은 **반드시 `Domain` 계층에서 시작**됩니다.

- **애플리케이션의 심장:** `Domain`은 외부 요인과 분리된 핵심 비즈니스 규칙을 담고 있습니다.
- **의존성 부재:** 다른 계층에 의존하지 않으므로, 외부 환경 없이 독립적으로 테스트와 개발이 가능합니다.
- **다른 계층의 기반:** `Infrastructure`와 `Application(Worker)` 계층은 `Domain`에 정의된 인터페이스와 로직에 의존하므로, `Domain`이 먼저 개발되어야 합니다.

## 4. 외부 데이터와 Domain 개발의 관계: 인터페이스와 추상화

**"어떻게 외부 데이터를 모르고 Domain 로직을 먼저 개발하는가?"** 라는 질문에 대한 답은 **인터페이스(Interface)를 이용한 추상화**입니다.

1.  **Domain은 '요구사항'을 정의합니다:** `Domain`은 외부 시스템의 데이터 구조를 신경 쓰지 않고, 자신이 원하는 이상적인 데이터 형태(엔티티)와 그 데이터를 가져올 방법에 대한 '계약서'(인터페이스)를 먼저 정의합니다. (예: `IBrokerService`와 `GetCurrentPortfolioAsync()` 메서드)
2.  **Infrastructure는 '의무'를 이행합니다:** `Infrastructure` 계층은 `Domain`이 정의한 인터페이스라는 계약서를 실제로 구현합니다. 외부 API의 복잡한 데이터를 `Domain`이 원하는 이상적인 객체로 '변환(Adapt)'하는 책임을 집니다.
3.  **TDD와 Mock 객체:** `Domain`을 테스트할 때는 실제 `Infrastructure` 구현체 대신, 인터페이스를 흉내 내는 가짜 'Mock 객체'를 사용하여 외부 의존성 없이 로직을 완벽하게 검증할 수 있습니다.

## 5. 아키텍처와 협업: PM과의 소통은 어떻게 하는가?

클린 아키텍처는 문서화와 협업을 지연시키는 것이 아니라, 오히려 **역할을 명확히 하여 촉진**합니다.

- **"비즈니스 규칙" vs "워크플로우":**
    - **`Domain`:** "무엇을" 계산하는지에 대한 순수 규칙 (PM이 세부 공식까지 알 필요 없음)
    - **`Application(Worker)`:** "어떤 순서로" 일이 일어나는지에 대한 워크플로우 (PM이 주로 관심을 갖는 부분)

- **문서가 개발을 주도한다:**
    - 기획자/PM이 먼저 `docs/04_WORKFLOWS.md`와 같은 **요구사항 문서를 작성**하고 팀과 합의합니다.
    - 개발팀은 이 문서를 **입력값**으로 삼아 `Domain` 로직과 `Application` 워크플로우를 구현합니다.
    - 개발이 완료된 `Application` 코드는 그 자체로 **가장 정확하고 살아있는 최신 버전의 '살아있는' 문서**가 됩니다.

- **협업의 장점:**
    - **관심사 분리:** 각자 역할에 맞는 코드/문서에 집중하여 효율적인 논의가 가능합니다.
    - **유연한 변경:** 워크플로우 변경 시 `Application` 계층만 수정하면 되므로, 변경이 안전하고 빠릅니다.
