# TDD 학습 정리

이 문서는 QuantRebalancer 프로젝트에서 TDD(Test-Driven Development)를 학습하고 실전에 적용하기 위한 기준 문서다.
앞으로 TDD 관련 내용은 이 파일에 누적한다.

## 1. TDD란 무엇인가

TDD는 "테스트를 먼저 작성하고, 그 테스트를 통과시키는 코드만 작성하는 개발 방식"이다.
핵심은 테스트를 보조 수단이 아니라 설계 도구로 쓰는 것이다.

- 목표:
  - 요구사항을 코드로 명확히 고정
  - 과도한 구현 방지
  - 변경 시 회귀(regression) 빠르게 탐지
- 오해:
  - "테스트를 많이 쓰는 것"이 TDD는 아니다.
  - 핵심은 작성 순서와 피드백 사이클이다.

## 2. Red -> Green -> Refactor

TDD의 기본 사이클은 아래 3단계다.

1. Red
   - 실패하는 테스트를 먼저 작성한다.
   - 아직 구현하지 않았거나, 규칙이 맞지 않아 실패해야 정상이다.
2. Green
   - 테스트를 통과시키는 최소 코드만 작성한다.
   - 이 단계에서 설계 미화는 하지 않는다.
3. Refactor
   - 테스트가 통과한 상태를 유지하면서 구조를 개선한다.
   - 중복 제거, 네이밍 개선, 책임 분리 등을 수행한다.

원칙: 한 번에 큰 기능을 통째로 구현하지 말고, 매우 작은 규칙 단위로 반복한다.

## 3. Given / When / Then의 의미

Given / When / Then은 테스트를 읽기 쉽게 표현하는 구조(주로 BDD 스타일)다.
Hexagonal Architecture의 규칙이 아니라 테스트 작성 방식이다.

- Given: 전제 조건(초기 상태)
- When: 실행 행동
- Then: 기대 결과

예시(개념):
- Given: 현금 100만원, 주식 목표 70%, 현재 65%
- When: Smart Filling 실행
- Then: 주식 ETF 매수 추천이 생성됨

중요:
- `Red`는 TDD 단계이고,
- `Given`은 테스트 본문 구조다.
- 둘은 같은 개념이 아니다.

## 4. 좋은 테스트의 기준

- 테스트 이름이 비즈니스 규칙을 설명한다.
  - 예: `Should_Recommend_Buy_When_Stock_Is_Under_Target`
- 한 테스트는 한 규칙만 검증한다.
- 입력/행동/기대값이 명확하다.
- 외부 시스템(DB, HTTP, 실시간 시세, 시간)에 의존하지 않는다.
- 빠르게 실행된다(단위 테스트 기준).

## 5. 이 프로젝트에서 TDD 적용 순서

Hexagonal 구조를 전제로, 다음 순서로 개발한다.

1. Domain 테스트부터 작성
   - 포트폴리오 계산, 드리프트 판정, 매수/매도 추천 규칙
2. Application 유스케이스 테스트 작성
   - 입력 포트 호출 시 어떤 출력 포트가 어떤 순서로 호출되는지 검증
3. Infrastructure는 계약(Port) 준수 여부 위주로 검증
   - 외부 API 어댑터, DB 저장소, Notifier 연결
4. Worker는 조립과 스케줄 트리거 검증
   - 실제 비즈니스 규칙은 Worker에 넣지 않는다

## 6. 테스트 레벨 가이드

- Unit Test (우선순위 최고)
  - 대상: Domain, Application
  - 특징: 매우 빠름, Mock/Fake 사용
- Integration Test (선별적으로)
  - 대상: Infrastructure 어댑터, DB 연동
  - 특징: 실제 구현 연결 확인
- End-to-End 성격 테스트 (최소)
  - 대상: 핵심 플로우 스모크 검증
  - 특징: 유지비가 크므로 꼭 필요한 범위만

## 7. QuantRebalancer에서 먼저 잠궈야 할 규칙(핵심 제약)

아래 항목은 초기에 테스트로 고정해야 한다.

1. `AutoTradingTarget`에 없는 자산은 절대 매도하지 않는다.
2. Smart Filling은 부족한 자산(`Gap > 0`)만 매수한다.
3. Drift가 Threshold 이내면 리밸런싱 주문이 없어야 한다.
4. 계좌 간 자금 이동 필요 시, 주문 대신 이체 요청 알림을 생성한다.

## 8. Anti-pattern (피해야 할 것)

- 구현 코드를 먼저 쓰고 테스트를 나중에 붙이는 방식
- 테스트 하나에서 여러 규칙을 동시에 검증하는 방식
- 내부 구현 디테일(사설 메서드 호출 여부)에 과도하게 결합된 테스트
- 외부 API를 단위 테스트에서 직접 호출하는 방식
- Green 단계에서 과도한 일반화/추상화

## 9. 실전 작업 루틴 (주니어 개발자용)

기능 하나를 시작할 때 아래 루틴을 반복한다.

1. 규칙 1개를 문장으로 쓴다.
2. 실패 테스트 1개를 작성한다.
3. 테스트 실행 후 Red 확인.
4. 최소 구현으로 Green 만든다.
5. 리팩토링 후 전체 테스트 재실행.
6. 다음 규칙으로 이동.

## 10. 체크리스트

PR 또는 커밋 전에 아래를 확인한다.

- 테스트가 비즈니스 요구사항을 설명하는가
- 테스트 없이 추가된 분기(if/else)가 없는가
- Domain 코드가 외부 의존성을 직접 참조하지 않는가
- 실패 시나리오(에러/예외/경계값) 테스트가 포함됐는가
- 리팩토링 후에도 테스트가 빠르고 안정적인가
